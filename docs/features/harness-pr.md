# PR の作成・依頼ゲートつきマージ

## 概要

git と GitHub への書き込みを専用ツールにまとめた機能（フェーズ 5）。PR は確認なしで作り、マージはユーザーが依頼したときだけ、確認ダイアログを出して行う。拡張 `harness` の `flow/` が、メインエージェントにだけ登録する（サブエージェントには登録しない）。bash からの `gh pr create`（別名 `new`）/ `edit` / `merge` と、`gh api` での PR の作成・更新・マージは、ガードが依頼の有無にかかわらず拒否し、このツールへ誘導する（[harness-guards.md](harness-guards.md)）。

  - `tools.ts`（ツール一覧の出し入れ `syncActiveTools`）
  - `plan.ts`（`PrRecord`・`recordPr`）、`report.ts`（完了報告の PR の欄）

## `harness_pr_create`

今の作業ブランチを push し（`git push -u origin <ブランチ>`。force はしない）、PR を作る。open な PR が同じブランチにあれば更新する。確認は出さない。引数は `title`（必須）と `summary`（省略可。1〜3 文。省略するとコミットの件名から作る）。

### 拒否する条件

拒否は `isError` つきの結果で返し、直し方を書く。push も gh の呼び出しも行わない。

| 条件 | 返す案内 |
| --- | --- |
| git のリポジトリの外 | （リポジトリの中で使う） |
| detached HEAD | 作業ブランチを作って切り替える（`git switch -c feat/…`） |
| 既定ブランチ上（`config.defaultBranches` と `origin/HEAD` の指す先） | 作業ブランチを作って変更を移し、コミットしてからもう一度呼ぶ。コミットの分け方 |
| 未コミットの変更がある（未追跡を含む） | 先にコミットする。コミットの分け方（1 コミット 1 つの目的・ファイルまで・土台から・履歴の文体・秘密ファイルは add しない）。変更の一覧を添える |
| 既定ブランチとの差分のコミットが無い | コミットしてから呼ぶ |

差分のコミットは `origin/<既定ブランチ>..HEAD`（無ければローカルの既定ブランチ）で数える。どちらも取れないときは、数えずに進める。

### 本文の形

「概要・変更点・確認方法」の固定の形で、生成部分を `<!-- harness:begin -->`〜`<!-- harness:end -->` で囲む。

- 概要：`summary`（省略時はコミットの件名を「、」でつなぐ）
- 変更点：コミットの一覧（古い順）
- 確認方法：計画の直近の検証結果（コマンド・成功か失敗か・要約）。計画が無い、検証が無い、検証コマンドが無いときは「未検証」

更新するときは、既存の本文のマーカーの間だけを作り直し、外側（ユーザーが書いた内容）は残す。マーカーが無い本文（手で作った PR など）は、元の本文を残して末尾に生成部分を足す。題名は渡された `title` で置き換える。

### ブランチ保護の確認（決定 007）

PR を作る前に、既定ブランチが GitHub で保護されているかを `gh api` で確かめる。**作らない**（書き込みの `gh api` は呼ばない）。

- ルールセット：`repos/<owner>/<repo>/rules/branches/<既定ブランチ>` に `pull_request`（PR 必須）の規則があれば保護
- ブランチ保護：`repos/<owner>/<repo>/branches/<既定ブランチ>/protection` が成功すれば保護
- どちらも無いと確かめられたとき（404）は未保護。ツールの結果に「注意: 既定ブランチ(main)が GitHub で保護されていません…」と書き、先へ進む
- 確かめられないとき（認証・権限・通信、origin が GitHub ではない）は、「確認できませんでした」と書き、先へ進む
- 注意は、計画があれば PR の記録（`warning`）に残り、完了報告の PR の欄に「注意」として出る

### 計画への記録

計画があれば、`recordPr`（`merged: false`）で `plan.prs` に番号・URL・題名を記録して保存する。計画が無ければ記録しない。

## `harness_pr_merge`

PR を merge commit でマージする。引数は `number`（省略すると今のブランチの open な PR）。

### ツール一覧への出し入れ

ユーザーの入力に「マージ」「merge」がある実行でだけ、ツール一覧に出す（`setActiveTools`）。依頼の判定は `guards/merge.ts` の `mentionsMerge`・`nextMergeRequested` を使う。

- `input` イベントで、ユーザーの生の入力（`/skill:…` の展開前）を見る。待機中の新しい入力では置き換え、実行中の追加入力（steer / followUp）では足す（依頼の無い状態から有る状態に変わる）。拡張が送った入力は数えない。結果は `Runtime.mergeRequested`
- 依頼は、その実行の間だけ有効。実行が終わったら（`agent_settled`）`Runtime.mergeRequested` を戻し、ツール一覧から外す。`/plan resume` で始めた実行は `input` を通らないので、`harness_pr_merge` は出ない。マージには、改めて「マージ」「merge」を含む依頼が要る（決定 003 の「依頼が無ければダイアログも出さない」に合わせ、安全側に倒した。[決定 012](../decisions/012-merge-gate-without-plan.md)）。依頼を数えたのに実行が始まらなかった（認証切れなど）ときに持ち越さないよう、`/plan resume` で再開するときにも戻す
- 確認ダイアログで拒否されたら、`Runtime.mergeDeclined` に覚え、その実行の中では、呼び直してもダイアログを出さずに止める（「この依頼ではユーザーがマージを拒否しました」）。自律ループが呼び直して、ダイアログが繰り返し出ないようにするため。依頼と一緒に、`agent_settled` と `/plan resume` で戻す
- ツールは `defaultActive: false` で登録し、`session_start`・`session_tree` でも、状態から出し入れを決め直す
- 出し入れは `flow/tools.ts` の `syncActiveTools` の 1 か所で組み立てる。今のツール一覧から「管理対象のうち不要なもの」を外し、「必要で無いもの」を足す。管理対象は `ask_user`（自律で進めている間は外す）と `harness_pr_merge`（依頼があるときだけ出す）の 2 つで、互いの変更を消さない。ほかのツールはそのまま残す。サブエージェントでは何もしない

### 実行時の流れ

1. 依頼の有無を、実行時にも確かめる（`Runtime.mergeRequested`）。無ければ止める。この実行の中で一度拒否されていれば（`Runtime.mergeDeclined`）、ダイアログを出さずに止める
2. UI が無ければ止める（CI を待つ前に確かめる）
3. PR を決める（`number` か、今のブランチの open な PR）。open でなければ止める
4. CI を待つ（`gh pr checks --json name,bucket`。15 秒ごと。実行中は 20 分、チェックがまだ登録されていない間は 60 秒が上限。中断できる。中断は、gh を呼ぶ前と CI の判定の前に見て、中断されていれば gh を呼ばず・判定せずに止める）。結果の判定は `pr.ts` の `judgeChecksResult`：
   - 標準出力が JSON の配列なら、その中身で判定する（`skipping` は無視、`cancel` は失敗）
   - 「チェックが無い」（`none`）とするのは、終了コード 1 で、標準エラーが gh の `no checks reported on the '<ブランチ>' branch`（または `no required checks reported …`）のときだけ（gh 2.102.0 で確かめた文言と終了コード）
   - それ以外（通信・認証・権限・gh が無い・出力を読めない）は「取得できず」（`error`）として、待たずに止める
5. ゲートを判定する（下）。止める理由があれば、確認ダイアログを出さずに止める
6. 確認ダイアログ（`ctx.ui.confirm`）に、PR の番号・題名・URL・CI の状態・注意を出す。許可されなければ止め、拒否を覚える
   - 拒否・ゲートで止めたときの結果には「計画にマージの項目があれば、`plan_update` の `deferred`（理由：ユーザーが拒否した／止めた理由）にして、残りを進める」と案内を書く
7. 許可されたら `gh pr merge <番号> --merge` を実行する。**`--delete-branch` は付けない**（決定 012）
8. 計画があれば、`recordPr`（`merged: true`）で記録する（作成時の注意は残す）

### ゲート（止める理由と注意）

| 区分 | 内容 |
| --- | --- |
| 止める | サブエージェント、UI が無い、CI が失敗（`cancel` を含む）、CI が実行中のまま上限時間に達した、CI の状態を取得できない（`gh pr checks` が「チェックが無い」以外の理由で失敗した） |
| 止める（計画のゲート） | 計画が確定済みで、PR のブランチが今のブランチのとき：直近の検証が無い・失敗・古い（検証のあとに作業ツリーが変わった）、レビューが必要な項目があるのに承認されていない・古い、未着手・進行中の項目が残っている（ただし、計画の最後の項目が進行中なら数えない。マージの項目は計画の最後に置き、`in_progress` にしてから `harness_pr_merge` を呼び、マージが済んだら結果を根拠に `done` にするため） |
| 注意（止めない） | 確定した計画が無い、または PR が計画の作業ブランチのものではない（検証・レビューを確認できていない）、CI が無い、検証コマンドが無く未検証、計画のゲートが効くときにローカルの HEAD が PR の先頭と違う |

注意は、確認ダイアログの本文に出す。ユーザーが見て判断する（[決定 012](../decisions/012-merge-gate-without-plan.md)）。

### ブランチを消さないこと

マージ後に、ローカルもリモートもブランチを消さない（`--delete-branch` を付けない）。リモートのマージ済みブランチは GitHub Actions が消す。ローカルのブランチは、ユーザーが整理する。ガードも、push でのリモートブランチの削除を常に拒否している。

## 完了の合図と計画のツールとの整合

- `harness_pr_create`・`harness_pr_merge` の成功は、完了の合図の「成果物を作る操作」に数える（拒否・失敗は `isError` で返すので数えない。[harness-instructions.md](harness-instructions.md)）
- `plan_propose` の説明、自律ループの継続のメッセージ、`main.md` の「Git操作と PR」「作業の進め方（PDCA）」が、この 2 つのツールで書いてある。マージの項目は計画の最後に置き、着手時に `in_progress` にしてから `harness_pr_merge` を呼び、マージが済んだらその結果を根拠に `done` にする、と書いてある。`pr` スキルは削除し、コミットの分け方などのルールを `main.md` に移した
- `plan_report` の PR の欄は、`plan.prs` に記録があるときだけ出る

## 既知の制約

- 実際の GitHub での動作（PR の作成・マージ・保護の確認）は、テストでは `gh` を差し替えて確かめている。実機での確認はユーザーが行う
- `gh pr checks` の出力に頼る。チェックが登録される前の PR は、60 秒待って「CI なし」の注意になる。「チェックが無い」の判定は gh のメッセージ（`no checks reported`）と終了コード 1 に頼るので、gh がこの文言を変えると「取得できず」として止まる（安全側）
- 通信の一時的な失敗でも、CI の状態を取得できなければ待ち直さずに止める。ユーザーがもう一度依頼する
- マージの依頼は実行ごと。計画にマージの項目があっても、一時停止して `/plan resume` で再開した実行では `harness_pr_merge` は使えない。ユーザーがもう一度「マージ」を依頼する必要がある（指示では、そのときマージの項目を `deferred` にする）
- 確認ダイアログで拒否すると、その実行の中では取り消せない（実行中に「やっぱりマージして」と送っても止まる）。実行が終わってから、改めて依頼する
- ブランチ保護の判定は「PR 必須の規則があるか」だけを見る。force push の禁止や必須のチェックの有無は見ない
- マージの依頼の判定は語の照合。否定文（「マージはしないで」）でもツールが出る（呼んでも、確認ダイアログで拒否できる）
- 計画のゲートは、PR のブランチが今のブランチのときだけ効く。別のブランチの PR は、注意として出るだけ
- ローカルの HEAD と PR の先頭の比較は、計画のゲートが効くときだけ行う
- マージ後は、ローカルのブランチと作業ツリーはそのまま。既定ブランチへの切り替えと最新化は、ユーザーまたは `git-pull` スキルで行う
- PR の更新で本文を置き換えるのは、マーカーの間だけ。題名は常に渡された `title` になる
