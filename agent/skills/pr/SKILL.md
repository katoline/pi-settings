# PR作成

現在の作業内容をコミットし、GitHub へ Pull Request を作成する。マージはこのスキルの範囲外。

## 0. 検証

プロジェクトの `AGENTS.md` / `CLAUDE.md` に検証コマンド（lint・型チェック・テスト・ビルド等）があれば実行する。通らなければコミットせず、失敗内容を報告して止める（テストの skip や期待値の書き換えで通さない）。検証コマンドが書かれていなければ「未検証」として進め、報告と PR 本文に明記する。

挙動に関わる変更（コード・フック・設定）なら、グローバル指示（`~/.pi/agent/AGENTS.md`）の「独立レビュー」節のレビューが済み、採用した指摘を直してあることを確かめる。済んでいなければ先に行う。

## 1. 現状把握

- `git status` で未コミットの変更・未追跡ファイルを把握する。`.env` や鍵・トークンなどの秘密ファイルが含まれていないか確認する
- `git diff` / `git diff --staged` で変更内容を把握する
- `git log --oneline -10` でコミットメッセージの文体を把握する
- 現在のブランチ（`git branch --show-current`）と既定ブランチ（`git symbolic-ref --short refs/remotes/origin/HEAD` の `origin/` 以降。取得できないときのみ `gh repo view --json defaultBranchRef --jq .defaultBranchRef.name`）
- 未 push のコミット：`git rev-parse --abbrev-ref @{upstream}` が失敗（upstream 未設定）なら全コミットが未 push。成功したら `git log @{upstream}..HEAD --oneline`
- 作業ブランチに open な PR があるか：`gh pr list --head <ブランチ> --state open --json number,url`。マージ済みの PR しかないブランチに追加の変更があるなら、`git fetch origin` してから既定ブランチの最新から新しいブランチを切り直す

未コミットの変更も未 push のコミットもなければ、PR にするものがない旨を報告して終える。

## 2. ブランチ準備

- 既定ブランチ上にいる場合は、変更内容を表す新しいブランチを作って移動する（例: `feat/xxx`、`fix/xxx`、`docs/xxx`、`chore/xxx`）
- 既に作業ブランチ上ならそのまま使う

## 3. コミット

後から参照・`git revert` しやすいよう、未コミットの変更を目的ごとに分けて複数コミットにする（秘密ファイルは add しない）。

- **分け方**：1コミット = 1つの目的（機能追加・修正・設定変更など）。ファイルの種類では分けず、変更とそれに追従するドキュメント・テストは同じコミットに入れる。一緒に変えないと壊れるものは必ず同じコミットにする。小さな修正は関連するコミットに含め、細かくしすぎない
- **単位はファイルまで**：`git add -p` 等で1ファイルの変更を分割しない。1ファイルが複数の目的にまたがる場合は主な目的のコミットにまとめ、報告に書く
- **順序**：各コミットがその時点で単体で成り立つよう、依存される側（土台）から先にコミットする
- **進め方**：最初に `git diff --staged --name-only` を確認し、ステージ済みのファイルがあれば `git restore --staged <ファイル>` で外してから、コミットごとに `git add <ファイル…>` → `git commit` を繰り返す。最後に `git status` で取り残しが無いことを確認する
- 今回の作業と無関係な変更が混ざっている場合は、それをコミットに含めず、残したことを報告に書く
- 変更全体が1つの目的なら1コミットでよい
- コミットメッセージはそのコミットの目的だけを要約し、既存の履歴の文体に合わせる（無ければ日本語の簡潔な1行要約）

## 4. Push と PR

- `git push -u origin <ブランチ名>` で push する
- open な PR が**無ければ** `gh pr create --base <既定ブランチ>` で作成する
  - タイトル：変更内容の要約
  - 本文：変更の概要、変更点の箇条書き（複数コミットならコミットごとの内容が分かるように）、検証結果（未検証ならその旨）。`--body "$(cat <<'EOF' … EOF\n)"` の HEREDOC で渡す
  - `.github/pull_request_template.md` があればその構成に従う
- open な PR が**あれば**、新規作成せず、タイトル・本文を全体として作り直して更新する
  - `gh pr view <番号> --json commits --jq '.commits[].messageHeadline'` で PR に含まれる全コミットを GitHub 側から取り、上と同じ基準で作り直す（今回分の追記ではなく全体の作り直し）
  - 先に `gh pr view <番号> --json title,body` で現在の内容を読み、自分が生成していない記述（ユーザーが書いたレビュー依頼・関連 Issue・補足など）があれば作り直した本文にも残す
  - `gh pr edit <番号> --title "<タイトル>" --body "$(cat <<'EOF' … EOF\n)"` で更新する

## 5. 報告

作成（既存 PR なら更新）した PR の URL・ブランチ名・コミットの一覧（分け方の意図と、複数の目的にまたがるためまとめたファイルがあればそれ）・検証結果（未検証ならその旨）を簡潔に報告する。

## してはいけないこと

- PR のマージ（`gh pr merge`・`gh api` でのマージ）。ユーザーがその PR のマージを明示的に指示したときだけ実行する（依頼が無ければ `git-guard` 拡張がブロックし、依頼があれば確認ダイアログを出す）
- force push・`--no-verify`・既定ブランチへの commit / push・リモートブランチの削除（`git-guard` 拡張がブロックする。ブロックされたら回避策を探さず、作業ブランチで進め直すか報告する）
- `--amend` などの履歴の書き換え（ユーザーの明示的な指示があるときだけ）
- `gh` が未認証・リモート未設定などで失敗した場合に、勝手に回避策を取ること。状況を報告して止める
